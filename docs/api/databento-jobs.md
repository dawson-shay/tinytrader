# databento-jobs

| | |
|---|---|
| **Purpose** | Buy historic DBN from Databento's batch API, with a quoted price and an exact confirmation before any charge, then download each finished job and file it in the [store](store.md). |
| **Transport** | HTTP/1.1, JSON, on `JOBS_LISTEN` (default `127.0.0.1:9121`). |
| **Versioning** | Unversioned paths; additive changes only. |
| **Auth** | Writes are refused from a web page of another origin; bind to loopback or a private network. A charge needs a person's approval through the [console](console.md): the bearer token `JOBS_APPROVE_TOKEN`, `approved_by`, and `confirm_usd` equal to the quoted price. Free requests need none of it. It writes to the store with `JOBS_STORE_TOKEN` (or `_FILE`). |
| **Errors** | `{"error": "..."}`: `400` invalid request, `403` a paid purchase without approval, `409` stale, changed, declined or still-pricing quote, or nothing left to buy, `428` confirmation needed, `503` no ledger configured, or what's had can't be read in full, `502` Databento failed or quoted a price that isn't a number of dollars. |
| **Health** | [Observe](observe.md) endpoints and `/events`. `idle` while it yields to live capture. |
| **Stability** | **Experimental.** |

## Configuration

| Variable | |
|---|---|
| `DATABENTO_API_KEY` (or `_FILE`) | Required. |
| `JOBS_STORE` | The store (default `http://127.0.0.1:9120`). |
| `JOBS_LEDGER` | The submissions ledger file (JSON lines, appended); without it nothing can be submitted. The service holds an exclusive lock on `<ledger>.lock` while it runs and refuses to start if another process holds it. Keep it on a local disk, never on a network filesystem shared between hosts: the lock only guards one host. |
| `JOBS_YIELD_TO`, `JOBS_CAPTURE_HOURS`, `JOBS_CALENDAR` | Hold downloads while capture is live (as the [queue](queue.md) does). |
| `JOBS_REFRESH_SECONDS` | How often Databento's job list is read (default 30). |
| `JOBS_DOWNLOADS` | Jobs downloaded at once (default 4; `--downloads`). Each job files as soon as its download is done; the store files them one at a time, grouping those that wait. |
| `JOBS_CACHE_DIR` | Where `POST /cache/{job}` puts jobs' files (`--cache-dir`; default `cache/` beside `JOBS_LEDGER`). |
| `JOBS_APPROVE_TOKEN` (or `_FILE`) | The token a paid purchase's approval carries, shared with the console (`CONSOLE_JOBS_APPROVE_TOKEN`). Unset, paid purchases are refused (`403`); free ones still go through. |

## Day conditions

Once at start and once a day (background work, waiting while capture is live), the service asks Databento for the day conditions (`available`, `degraded`, `missing`; `pending` days are left for the next day) of each Databento dataset the store holds (catalog provider `databento`, or none, and on Databento's dataset list), over the first to last day held, at most 1,000 days a call. It sends them to the store's `POST /conditions/databento` (`[{dataset, day, state, last_modified}]`, with `JOBS_STORE_TOKEN`), one call per dataset, and turns each change the store reports (`{"changed": [{dataset, day, volume, folder, from, to}], "unchanged", "not_held"}`; `from` is `null` when no condition was recorded) into an event, such as `OPRA.PILLAR 2024-06-03: degraded → available (on M2-A), re-released 2024-07-01`, the release date being the one sent. Databento repairs degraded days and releases them again: when the store holds such a day from a batch (its condition's `source` in `/coverage`, read before it is replaced, is `batch <id>`, or the catalog lists it in an unfiled `databento batch` download), the event says downloading it again may be worth it. Nothing is bought. Failures are logged and tried again the next day.

## Endpoints

**A person approves every paid purchase** ([decision 0019](../decisions/0019-purchase-guards.md), with approval in the console instead of a machine-bound key): a quote that costs anything waits (60 minutes, against 15 for a free one) until it is approved or declined in the console's Jobs widget. The console sends `/submit` with the approval token, the login that approved it as `approved_by`, and the price it showed as `confirm_usd`. The ledger records an `approved` step (who, when, the quote, the cost) before each request is sent.

**What's had already** (decision 0019, section 2) is one set, used by pricing and submitting alike, per day, per contract and per time window: the store's Databento holdings (`/coverage`, and any day `/catalog` holds that `/coverage` doesn't explain, as held in full); every job on Databento's list that isn't expired (the list read in full: every state, all history); and every purchase in the ledger, whether or not its job is still listed, including submissions whose outcome isn't known. Job and ledger symbols are parsed: a list naming the parent or `ALL_SYMBOLS` covers it all, contracts of the parent count one by one, and instrument IDs or anything unreadable cover every day they overlap. Every read of the store (`/catalog`, `/coverage`, `/files`) has a 120 s limit, and is tried up to three times (after 2 s, then 8 s) when its connection drops, its answer is cut off or unreadable, or the store answers 503; not after a timeout. Writes to the store are never retried this way. Pricing uses the store's last scan; under the purchase lock, `/submit` re-checks against a fresh one (`fresh=1` on `/catalog` and `/coverage`, which the store waits up to 600 s for; 660 s limit). A partial day is held contract by contract over each of its coverage `pieces` (`[{symbols, window}]`; without them, its one `symbols` and `window`); a day being merged (`pending`) is held in full until it settles. Copies outside Databento's folder (`provider: null` in the catalog) are never taken as accounted for by `/coverage`: a day with such a copy counts as held in full. Every purchase is refused (`503`) while the store answers anything but `200`, reports `missing_volumes` (or doesn't report them), or Databento's job list or any listed job can't be read. The one exception is a request with `free_ignore_held: true`: it doesn't ask the store what it holds, so it may buy again what the store has (for the plan's free data while the store can't answer); it skips only the days a whole job of the symbol on Databento's list (the download center), or bought here, already covers, and buys every other day whole, and only if it is free: a quote that costs anything is refused (`409`), at pricing and again at submitting. A request with `price_only: true` is only priced: every day whole, without asking the store, Databento's job list or the ledger what is held (so it may include what is), at any price, with no rule or contract lists (they need the store's definitions). Its quote can't be submitted (`409`): an estimate while the store can't answer. Datasets are compared in Databento's spelling and must be on its dataset list. One purchase runs at a time: `/submit` holds one lock from their last check through the ledger's last write, and reconciliation waits while a purchase is in flight. Every Databento call is bounded (60 s for reads, 120 s for a submission, which is then written `uncertain`). A submission is matched to a job received after its `sending` step (less two minutes). A `not-submitted` that an earlier version wrote on its own counts as unresolved again; the service logs each at startup.

| Endpoint | |
|---|---|
| `GET /jobs` | `{"jobs": [...], "store_reachable", "updated_at"}`. Each job: `id`, `state` (`queued`, `processing`, `done`, `expired`), `dataset`, `schema`, `symbols`, `stype_in`, `start`, `end`, `cost_usd`, `bytes`, `received`, `expires`, `held` (where the store has it), `transfer` (download progress, or `failed` with the store's or Databento's error), `unfileable` (why the store would refuse it). Times are integer Unix seconds. Jobs bought here download and file by themselves once done, up to `JOBS_DOWNLOADS` at once, never one job twice at once: a job of one symbol as a batch of it, a job listing contracts of one option parent (each a strict OCC symbol, by `raw_symbol`) as partial days of that parent (`/incorporate/databento/{id}?parent=ROOT.OPT`); jobs of several symbols otherwise aren't fileable. Before downloading, and again before filing, the store is asked whether it has filed the batch already (`/batches/databento`); if so nothing more is done. While the store rescans (its `/catalog` answers 503) a download waits, longer each time, up to 10 minutes. A failed download or filing (including a batch left in the store's incoming folder) is tried again after 1, 2, 4 and 8 minutes, 5 tries in all, then left `failed`, with an event each time; every 6 hours a job left failed gets 5 more tries. A done job not filed within 7 days of its expiry at Databento shows `expires_soon` and is told of once, as an event. A job of contracts merged into days the store holds needs room on each volume holding such a day (`/coverage` `volumes`) for both the new file and the day's file; until then it waits, saying which volume needs how much, for up to an hour. The store's `/catalog`, `/incoming` and `/coverage` reads for a download wait out a rescan (503) the same way, and `/incoming` has a 60 s limit. At start the service logs how many jobs submitted here (the ledger) it follows. |
| `GET /datasets` | `{"datasets": [...]}` |
| `GET /schemas?dataset=` | `{"schemas": [...]}` |
| `POST /price` | `{dataset, schema, symbol, stype_in?, start, end, rule? \| contracts?, hours?, again?, free_ignore_held?, price_only?}` → a quote (below). `symbol` is a parent (`SPY.OPT`, the whole chain) or a raw symbol; `stype_in` is `parent` (by default for a name with a dot) or `raw_symbol`. Days `start` to `end`, inclusive, at most 1,500. For an option parent only, `rule` (`expiries`: the first N expiries from each day; `dte_max`; `strike_min`/`strike_max` in dollars) or `contracts` (`{"YYYY-MM-DD": ["SPY   221021C00370000", …]}`: exactly these, each of which must be in the store's definitions of that day, `400` otherwise; days outside the range are `400`) buys by contract. `hours` (`{"start": "09:30", "end": "16:01", "tz": "America/New_York"}`, New York only, daylight saving applied per day) narrows each day to those hours. Only what's missing is priced: a day with nothing of the symbol had in its window is bought whole (consecutive whole days as one request; with `hours`, a request per day); of an option parent, a day partly had (or any day, with a rule or contracts) is bought as its missing contracts over the hours each still needs (split at 2,000), from the store's definitions of the day; of any other symbol, a day partly had isn't bought, and a note says why. `again: ["OPRA-…"]` names exactly the expired or no longer listed purchases here whose contracts and days may be bought again (`400` for any other, or for `true`); otherwise they stay subtracted, and the notes name them. Requests are priced 16 at a time, each on its own Databento client, each given up to 5 minutes and tried up to three times on a 5xx or no answer. `200` with the quote, or `202` with it still `pricing` when that takes over 20 s; a price not done in 4 hours becomes `failed`. Each request's price must be a number of dollars, at least 0: otherwise the quote's `cost_usd` is not a number, it needs approval, and it is never bought. Within a quote no two requests cover the same contracts and time (the plan is refused if they would); New York hours use the offset in force at each end, so whole days tile across the daylight-saving changes. |
| `GET /quotes`, `GET /quotes/{id}` | `{"quotes": [quote, …]}`, or one quote. A quote: `quote` (its ID, `q-<random per start>-<n>`, never repeated across restarts), `state` (`pricing`, `ready`, `failed` with `error`; once submitted, `submitting`, then `submitted` or `failed` with `error`, with `submitted` and `of`, the requests sent so far and in all, and `jobs`, the jobs made so far, kept for a day), `priced` and `of` (requests priced so far), `dataset`, `schema`, `symbol`, `stype_in`, `start`, `end`, `hours`, `rule`, `contracts` and `contract_days` (counts, for contract lists), `again`; once ready, `cost_usd`, `billable_bytes`, `needs_approval` (it costs anything), `valid_seconds` and `expires_at` (when it stops being good to submit, integer Unix seconds; it can differ by a second between reads), `notes` (what was skipped and why), and `requests`: each `{kind: "whole" (with symbol) \| "contracts" (with contracts, skipped_held, skipped_pending), first_day, last_day, window: [start, end], hours, cost_usd, billable_bytes, condition?}`; `condition` is the worst of Databento's conditions of its days (`missing`, `pending`, `degraded`) when any isn't available, and `notes` list those days. A window's ends are a date (midnight UTC) or RFC 3339. |
| `DELETE /quotes/{id}` | Declines a quote; needs the approval token (`403` otherwise). → `{"declined"}`. |
| `POST /submit` | `{quote, confirm_usd, approved_by?, again?}` → `{"submitted": [request…, each with its job], "cost_usd"}`. A quote is used once. Plans it again under the purchase lock, against a fresh scan of the store, and submits only if every request and the total are unchanged (`409` otherwise; `409` too when there's nothing to buy). A paid one needs the approval token as its bearer token and `approved_by` (`403`), and `confirm_usd` exactly the price (`428`); either refusal leaves the quote as it was, to be approved again. `again`, when given, must be exactly the quote's. Each request is written to the ledger before it is sent; a failure stops there and lists what was submitted. It runs to its end even if the caller goes away; its progress shows in `GET /quotes/{id}`, and a refusal or failure is an event with its reason and how far it got. To buy the rest of one that stopped, price the same request again: what was sent is subtracted (a request whose outcome isn't known too, until resolved), so only the rest is quoted. Jobs of contract lists are filed as partial days of the parent (`/incorporate?parent=`, decision 0018). Its requests are submitted 3.5 s apart, as Databento takes at most 20 submissions a minute: a quote of 789 requests takes about 46 minutes. |
| `GET /ledger/unresolved` | `{"unresolved": [entry, …]}`: every submission whose latest ledger step is unresolved (`sending` or `uncertain`, or a `not-submitted` an earlier version wrote on its own), as the ledger holds it (`at`, `request`, `state`, `note`, `quote`, …) plus `sent_at`, when that attempt was sent. These are what `POST /ledger/resolve` names. Reads only; `503` with no ledger configured. |
| `POST /ledger/resolve` | `{request, at, job, note}` → `{"request", "state", "job"}`. The operator's word on a submission whose outcome isn't known (its latest ledger step `sending` or `uncertain`, identified by its `request` fingerprint and `at`): `job` is the job it made (written `submitted`; it must be on Databento's list, for the request's dataset and schema, and not another submission's job, `409` otherwise), or `null` for none (`not-submitted`; `409`, saying when it will be allowed, until the submission was sent at least 30 minutes ago and a complete read of the job list begun after then hasn't found it). Nothing else ever writes `not-submitted`. `404` when there's no such unresolved step. |
| `POST /cache/{job}`, `DELETE /cache/{job}` | A copy of a done job's files outside the store, for reading while the store can't file them (a drive away, say). `POST` queues the job and answers at once: `202` `{"job", "folder", "state": "queued"}`. One worker then downloads queued jobs one at a time, in the order asked, into `JOBS_CACHE_DIR/<job>/` (by default `cache/` beside the ledger). Each file is written as `<name>.part`, checked against Databento's size and SHA-256, then renamed, readable by everyone. Databento's file list is written as `manifest.json` (its own list usually includes one, which arrives like any other file), and `COMPLETE` (`{job_id, files, bytes, finished_at}`) last: the folder is whole once `COMPLETE` is there. Files already there and whole are kept. While capture is live the worker waits, so a request made then is queued and runs once capture ends. A request leaves a `REQUESTED` marker in its folder until it has ended, so a restart takes it up again. A network error, a file cut short, or Databento's 429 or 5xx is tried again later (every 15 s, doubling to 10 minutes), never failed; only an error that won't change (another 4xx, a whole file with the wrong hash, a disk error) fails the job. The key stays in the service; nothing is filed or bought. `409` until the job is done, or while it is queued or caching; `503` with no cache folder, or with 256 requests already waiting. `DELETE` removes the job's folder (`404` if there's none, `409` while queued or caching). Its end is an event. |
| `GET /cache` | Every cache request since the service started: `{"cache": [{job, state, position, file, done_bytes, total_bytes, error, requested_at}], "queued", "capacity"}`, in the order asked. `state` is `queued` (with `position`, how many are ahead), `starting`, `waiting: …` (capture is live, or starts before the file could finish), `downloading`, `retrying: …`, `cached`, or `failed` (with `error`). The job's `cache` in `GET /jobs` shows the same. |
